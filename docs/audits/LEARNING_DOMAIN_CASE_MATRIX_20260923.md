# AskATutorLive Learning Domain Case Matrix

Date: 2026-09-23  
Status: discovery baseline; implementation and runtime verification are separate states.  
Scope: repository source, requirements, decision records, migrations, generated Supabase types, and tests. Production or non-production data was not modified for this discovery.

## Authority and reading rules

- Confirmed product requirements are in `docs/PRODUCT_CONSTITUTION.md` and `docs/CONFIRMED_REQUIREMENTS.md`.
- D-0005 accepts a bounded learning/assessment target model. It does not settle instrument content, affective retention/consent, mastery expiry, or institution reporting. See `docs/DECISION_LOG.md` and `docs/architecture/LEARNING_ASSESSMENT_DESIGN.md`.
- Architecture proposals and historical docs describe targets, not proof of runtime behavior. Source, migrations, policies, generated types, and tests establish implementation state.
- `MISSING PRODUCT DECISION` means engineering must not choose a product rule or numerical limit.
- Evidence status is scoped to the evidence named in the row: `VERIFIED` means direct source/schema/test evidence establishes the claim; `PARTIALLY VERIFIED` means the observed path is incomplete or runtime evidence is missing; `INFERRED` means documentation or indirect evidence supports the claim; `UNKNOWN` means no reliable current behavior or rule is established; `BLOCKED` means required verification is unavailable.
- Source-level verification is not a substitute for runtime database verification. Rows marked `BLOCKED` still include source findings where available.

### Virtual Lab lifecycle boundary summary

- The only durable Labs artifact is a saved simulation definition, not a session, runtime state, result, measurement, reflection or assessment attempt.
- A library re-entry starts a fresh simulation from the saved definition. Calling it “resume” would overstate current behavior.
- The newer deterministic `src/domain/lab` mechanics code and its validation functions are not wired into the existing Simulation Lab route; current simulation renderers remain client-side.
- The prepared migration is statically reviewed, not runtime verified. It uses owner-derived writes, Labs/AI configuration checks, a private `SECURITY DEFINER` helper with empty `search_path`, a public authenticated `SECURITY INVOKER` wrapper, explicit grants, a unique idempotency key, and atomic version-1 creation. It also changes `match_simulations` to invoker security and pins the existing role/scope definer helpers to an empty search path. Function/RLS/table grants have not been applied or probed.
- The Free-tier local counter was removed because no confirmed amount/event/reset/account policy exists. The Labs feature scope remains the technical enforcement boundary; whether Free users should receive Labs access and any quota are `MISSING PRODUCT DECISION` items.
- Lab assessment, progress, mastery, tutor review, parent access, session recovery and evidence retention must not be implemented until D-0005/product authorities define the relevant meanings and permissions.

### Entitlement and persistence boundary findings

- UI `usePlatformConfig` still provides display defaults on query error, but `useEntitlements` now carries query failure and `ScopeGate` denies access with a verification error instead of interpreting defaults as open mode. Server-side `assertAiEntitlement` also fails closed when config, role, or scope reads fail. Treat UI as navigation only.
- `get_my_scopes()` checks active status, expiry, and active plan, but the source query does not check `subscription_assignments.starts_at`. The current admin plan flow defaults starts to now; whether future-dated assignments are supported requires source/data verification before changing this RPC.
- New simulation saves fail closed at the app boundary and the repository now uses a UUID-keyed atomic simulation-plus-version RPC. The prepared migration revokes direct INSERT; prevents simulation UPDATE until a versioned edit path exists; makes version rows read-only to authenticated users; and exposes an authenticated `SECURITY INVOKER` wrapper that calls a private, pinned-path `SECURITY DEFINER` helper. The helper repeats AI/Labs/open-mode/role checks, derives owner from `auth.uid()`, validates bounded top-level schema structure, and handles retries through a unique owner/request key. The migration is unapplied; raw authenticated INSERT/UPDATE remain allowed by prior source policies until it is applied.
- Existing simulation list/delete remain owner-isolated and ungated pending a saved-work expiry decision. Application-level edit, version-history retrieval, and resume-of-execution paths do not exist. Reopening a saved library item starts from its definition and resets runtime state.
- The unsupported browser-only lab counter has been removed; the Free quota, if any, remains undefined and unenforced. No quota/reset quantity has been added.
- No AI quota exhaustion test is possible until the usage semantics and accounting are implemented. Current tests cover scope allow/deny and fail-closed configuration, not a nonexistent quota ledger.

### Assignment and submission integrity findings (source-verified; migrations not applied)

The existing `assignment_submissions` INSERT policy checks `student_id = auth.uid()` but does not verify assignment ownership or the student role. Its UPDATE policy permits the student to write grading columns. Migration `20260923110000_harden_assignment_submission_ownership.sql` adds assignment ownership checks and separates student updates to ungraded rows from tutor/admin review. The pre-existing student DELETE policy still permits deletion of the learner's own submission; resubmission/deletion behavior is a product gate, so this migration leaves it unchanged.

The assignment page also exposes a learner “Mark done” action that previously attempted a direct table UPDATE, while the only `assignments` UPDATE policy allows tutors/admins. The route now calls `complete_own_assignment(uuid)`, authored in migration `20260923123000_secure_learner_assignment_completion.sql`. The RPC requires the student role, scopes the update by `auth.uid()`, changes only `status`, returns success for repeated completion, does not reveal whether a foreign assignment exists, and is executable only by `authenticated`. This is a local source fix; both assignment migrations are unapplied and have no runtime verification because the configured non-production Supabase project is inactive and Supabase CLI/Docker are unavailable on this host.

The saved-simulation tables currently grant `INSERT` to `authenticated` and rely on owner-only policies, allowing direct REST creation without the Labs application guard. Migration `20260923140000_enforce_simulation_entitlement_and_atomic_save.sql` revokes direct table INSERT from `PUBLIC`, `anon`, and `authenticated`. Its authenticated-only security-definer RPC checks authentication, AI availability, and Labs scope or an allowed privileged/open-mode case before inserting both the simulation and version 1 in one transaction. The repository calls this RPC instead of issuing two independent inserts, one of which previously ignored its returned database error. The migration has not been applied or runtime exercised.
